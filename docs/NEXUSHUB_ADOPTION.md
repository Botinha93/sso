# Adopt NexusID into NexusHub

NexusHub can use an existing NexusID deployment through its standard OpenID Connect issuer. Adoption is additive: it registers one dedicated confidential OAuth client for Hub sign-in. It does not provision, migrate, reset, or delete user accounts; change signing keys; create user roles or app assignments; or replace NexusID's standalone authorization and token endpoints.

## What the installer can configure

The installer can check the configured issuer's authorization, token, JWKS, and registration endpoints through `/.well-known/openid-configuration` before receiving any operator credential. Discovery responses are limited to 256 KiB and registration responses to 64 KiB, with actual streamed bytes checked even when `Content-Length` is absent or inaccurate. Run `npm run nexushub:preflight` with `NEXUSID_ISSUER` and `NEXUS_PUBLIC_ORIGIN` set. `NEXUS_PUBLIC_ORIGIN` must be an origin only (scheme and host, with an optional port), without a path or query; the callback path is fixed by the reviewed profile. This is a read-only discovery request: it sends no bearer token, creates no local reservation, and makes no client change. It also requires discovery to explicitly advertise the `client_secret_post` method used by Hub; absent metadata is treated as incompatible rather than assuming an OAuth default the Hub does not use. Registration requires NexusID's dynamic registration mode to be `admin`. The request uses NexusID's existing broad `clients:add` permission, and requests `authorization_code`, `refresh_token`, and `token_exchange` grants. That permission can register arbitrary OAuth clients; NexusID currently has no narrower Hub-only provisioning permission, registration profile type, or profile lookup. Use a dedicated, short-lived operator credential, enable admin registration only for the provisioning window, and revoke the credential/disable registration afterward. The CLI does not request user, role, application assignment, or signing-key administration. Version 1 of [`config/nexushub-oidc-profile.json`](../config/nexushub-oidc-profile.json) is the scope source of truth: it grants identity scopes `openid profile email` plus nine individually named Hub scopes under `hubScopes`. The registration script validates the profile identifier/version and sends exactly those names; it grants no wildcard or NexusID administration scope. Authorization code flow is PKCE-required by NexusID.

The registration produces an opaque client ID and secret. Save them as Hub server-side credentials; do not put the secret in browser code, source control, a public app manifest, or a URL. NexusHub must use the exact callback URL registered here. NexusID validates redirect URLs against its normal client/instance policy. Existing deployments that reject the callback should be fixed by an administrator through the supported policy; do not weaken redirect validation for Hub. After read-only discovery succeeds, the CLI reserves the private output path with exclusive creation. A completed config prevents accidental duplicate registration on a repeated invocation. The registration endpoint must share the issuer origin because the operator bearer token is sent to it. Redirects are rejected so the bearer credential cannot be forwarded to a different origin. A network error, timeout, server error, incomplete response, or local credential-write failure retains a `registration_in_progress` marker; inspect NexusID Admin and either recover/configure the issued client or remove it before deleting the marker and retrying. The current NexusID handler returns 400/401/403 before client creation, so these explicit rejections remove the reservation and can be corrected and retried. This is safe retry classification, not automatic retry.

Mutating adoption also requires `NEXUSID_ACKNOWLEDGE_BROAD_CLIENTS_ADD=true`. This explicit operator acknowledgement is required because the currently supported RFC 7591 route has broader `clients:add` authority and is non-idempotent. It does not grant NexusHub that permission or make the flow suitable for unattended, automatic installation. Read-only `nexushub:preflight` does not require the acknowledgement.

Example, run from this repository on a trusted operator machine:

```sh
export NEXUSID_ISSUER='https://id.example.com'
export NEXUSID_ADMIN_ACCESS_TOKEN='…'
export NEXUS_PUBLIC_ORIGIN='https://hub.example.com'
export NEXUSHUB_OIDC_CONFIG_OUT='/etc/nexushub/nexusid-oidc.json'
export NEXUSID_ACKNOWLEDGE_BROAD_CLIENTS_ADD=true
npm run nexushub:adopt
```

Preflight example (no operator token and no output path required):

```sh
export NEXUSID_ISSUER='https://id.example.com'
export NEXUS_PUBLIC_ORIGIN='https://hub.example.com'
npm run nexushub:preflight
```

The CLI contract is exercised by `tests/unit/nexushub-adoption-cli.test.ts` against a local OIDC issuer fixture. It verifies that preflight makes only the discovery request, that an unacknowledged mutation stops before registration, and that a successful registration sends the reviewed grants/scopes and writes the secret to a mode-0600 config without printing it.

The callback is derived as `${NEXUS_PUBLIC_ORIGIN}/auth/callback`, matching the Hub server configuration. The NexusID adoption script pins `redirectPath` for profile v1 to exactly `/auth/callback`; a future callback route change requires a reviewed profile version and Hub release together. The output is created exclusively (an existing path is never overwritten) with owner-only permissions. It contains the discovered OIDC endpoints, registered client ID and secret, exact callback, and requested scopes. The script does not print the secret. If the client registration succeeds but the local config cannot be written, the command reports that the new client must be removed in NexusID Admin before retrying.

NexusID's registration handler stores the client-allowed scope names as supplied; it does not require the names to exist in the scope catalog. Before provisioning, an operator should add each entry in the profile's `hubScopes` array to NexusID Admin → Scopes, using its `name` and `description`. These exact nine entries make the custom scopes visible in discovery and the catalog. Scope catalog management is session/CSRF based, so the CLI deliberately does not try to create entries with its client-registration bearer token. Keep the identity scopes in `identityScopes` and the custom Hub entries in `hubScopes`; do not replace them with broad or wildcard scope grants. When the consumed Hub API permissions change, update the versioned profile and coordinate a client re-registration/rotation plan rather than silently widening an existing deployment.

### Identity and claim mapping contract

The v1 profile scopes are OAuth permissions, not organization or project membership claims. NexusID's `profile` scope may return `name`, `preferred_username`, `given_name`, `family_name`, and `picture`; `email` may return `email` and `email_verified`. Hub does not use these mutable profile fields as account keys or authorization inputs. Its login flow validates the ID token and access token and requires both `sub` values to match; Hub stores and authorizes the resulting subject against Hub-owned organization and project membership records. A registered client, requested Hub scope, email domain, or profile claim does not create that membership.

This profile does not define or issue a NexusID tenant, organization, project, or application-installation claim, nor a mapping from NexusID tenants/groups to Hub membership. Operators must provision Hub membership through Hub's supported organization administration. Do not add a custom claim mapping or infer memberships from `groups`, `roles`, or email until a versioned claim contract specifies its issuer, meaning, stability, and authorization semantics. This keeps direct NexusID clients and existing OIDC claim behavior unchanged while making the current Hub mapping explicit.

The client registration API issues a fresh client on each request and does not implement a Hub-specific idempotency key or lookup-by-profile operation. The local output reservation prevents routine repeat runs but cannot make a remote HTTP operation transactional or recover a lost one-time secret. A focused CLI test simulates an HTTP 500 after registration was attempted, then retries against the same output path: the `registration_in_progress` marker blocks a second POST until an operator reconciles the result in NexusID Admin. Remove obsolete Hub clients only after confirming they are unused. NexusID has no supported machine-readable client profile provisioning seam beyond RFC 7591 registration, so do not script direct database writes or invent a private endpoint. The concrete blocker and acceptance criteria for a future safe API are recorded in [the NexusHub client provisioning decision](./decisions/NEXUSHUB_CLIENT_PROVISIONING.md): NexusID needs a dedicated machine authority, issuer-established installation ownership, transactional named-profile semantics, and a safe secret recovery lifecycle. Do not treat `client_name` as an idempotency key because names are not unique identifiers.

## Operator and installer responsibilities

An operator must provide a reachable NexusID issuer and an administrator access token authorized to register clients. The installer must verify the discovery issuer matches the operator-supplied issuer, request only the required scopes/grants, persist the one-time returned secret privately, and fail without weakening OIDC validation if registration is unavailable. Configure the Hub server with the saved issuer, client ID, client secret, and callback. Keep the NexusID client secret on the Hub server.

The current NexusID APIs do not provide a Hub-specific enrollment endpoint or a transactional operation covering OAuth client creation and Hub secret storage. Therefore an installer can safely adopt OIDC using the existing admin-gated dynamic-registration endpoint, but it cannot autonomously bootstrap NexusID administrator credentials, users, app assignments, signing keys, or policies. Those remain explicit NexusID operator setup. This is intentional: NexusHub must not silently assume control of an existing identity tenant.

### Managed client provisioning (opt-in)

The original RFC 7591 path remains unchanged: `POST /connect/register` still uses its configured registration policy and generates a new random client on each successful request. It is still appropriate for independently managed clients, but the NexusHub installer must use the separate enrollment flow below when managed provisioning is enabled.

With `NEXUSID_NEXUSHUB_PROVISIONING_ENABLED=true`, a deployment administrator first binds one active service-identity credential to the Hub's canonical HTTPS origin. For LiberIDE, that administrator must also explicitly enroll its separate canonical HTTPS API origin as `liberideOrigin`; NexusID does not infer it from the Hub address or a client request. NexusID generates the installation UUID and pins `nexushub:1` (and `liberide:1` only when that second origin is supplied); only the enrolled credential, with the dedicated provisioning audience, can manage either profile. The additive `PUT /api/nexushub/v1/client-profile` endpoint derives callback, grants, scopes, and PKCE policy from the issuer's closed profile implementation. It does not accept `clients:add` as authority, nor infer ownership from a client name, app ID, callback, or profile field. It reserves one deterministic, profile-specific client ID per installation, so a retry after a lost response cannot create a second client. Reusing that ID with different settings or a different secret returns `409` and does not mutate the client.

The Hub generates and submits its own client secret over TLS; NexusID stores it using the issuer's existing OAuth-client secret handling and never returns it in this provisioning response, including replays and adoption. Keep the Hub copy in a private server-side secret store. `mode: adopt-existing` succeeds only when a deployment administrator explicitly bound an existing client ID during enrollment and its secret and complete registration exactly match the pinned profile; arbitrary NexusID clients cannot be claimed. This is intentionally a strict adoption rule. Existing standalone registration and direct deployment continue to work unchanged. The profile writes are idempotent through the OAuth client primary-key constraint; the endpoint does not implement secret rotation. To change the Hub secret, use NexusID's existing administrator client-management controls and coordinate a separately reviewed rotation procedure. See [the provisioning decision](./decisions/NEXUSHUB_CLIENT_PROVISIONING.md) for remaining lifecycle requirements.

The opt-in enrollment can also include a separate canonical `liberideOrigin`; it is issuer-admin supplied and independently pinned from the Hub's `publicOrigin`. This enables profile `liberide:1`, whose only callback is `${liberideOrigin}/api/auth/nexusid/callback`, with OIDC scopes `openid profile email`, the authorization-code grant, PKCE, and confidential-client authentication. The origin is returned as enrollment metadata, but the profile endpoint does not accept a caller-selected redirect, scope, grant, or name. It uses a distinct installation-derived client ID, supports idempotent ensure/adopt of an exact existing registration, and never returns the submitted client secret. LiberIDE's inspected server config requests only those three OIDC scopes and exchanges an authorization code at that callback; it does not show a refresh-token flow, so this profile does not grant `refresh_token` or NexusHub's `token_exchange`. This profile is available only when the NexusID administrator enrolled `liberideOrigin`; an existing Hub-only enrollment does not implicitly trust an IDE host. Enrollment remains a manual NexusID administrator action: create or enable the provisioning service identity, issue its credential, then bind that credential and both public origins in NexusID Admin. The installing Hub must protect and submit the profile-specific client secret; users complete the normal NexusID login/consent experience for the three OIDC scopes. This profile does not enable delegated Hub actions or grant app permissions.

## Standalone compatibility

The issuer's existing discovery, authorize, token, JWKS, UserInfo, logout, and client-management interfaces remain in place. Dynamic registration remains disabled by default and retains its existing `disabled`, `admin`, and `open` modes. Hub adoption only requires `admin` mode for the registration step; after registration the regular OIDC client flow does not depend on dynamic registration staying enabled.

For opt-in delegated user actions, NexusID implements the `nexushub:1` token-exchange profile separately from generic RFC 8693. Each Hub installation must use its own NexusID-issued OAuth client; the canonical installation ID for this profile is that client ID. The Hub sends `nexushub_profile=nexushub:1`, that ID, and one resource audience through the authorization request so the consent screen can show the exact target. NexusID rejects a different installation ID at authorization, consent capture, or exchange. An administrator must also assign the Hub client's trusted `resources` allowlist in NexusID Admin; the dynamic-registration CLI cannot choose resource audiences. Consent is captured by the existing session and CSRF-protected `/oauth/consent` endpoint and lasts 30 days. It persists the exact granted scope list per user/client/installation/resource tuple; later exchange requests cannot widen that list. Users can review scopes and revoke active grants in NexusID Account → NexusHub access. Administrators with `consents:delete` can revoke an exact tuple through `/api/admin/consents/nexushub-delegations`; the endpoint validates the installed OAuth client and its configured resource, audits the actor and target, and emits a revocation event. Resource display labels/descriptions are not yet managed as trusted metadata, so the consent screen currently presents the configured audience URI. Exchange requires a valid, unrevoked user access token issued to the same authenticated Hub OAuth client, a resource explicitly configured on that client, and an active grant for the exact tuple. The issued token carries only consented scopes, the one target audience, a fresh `jti`, a Hub actor claim, and a lifetime bounded by the source token and grant. This profile does not alter ordinary RFC 8693 requests.
