# Decision: NexusHub OAuth client provisioning

**Status:** Opt-in fixed-profile ensure/adopt API implemented; managed rotation and a normalized installation registry remain open
**Date:** 2026-10-22

## Decision

NexusID now exposes an opt-in fixed-profile machine API after an administrator enrolls a service identity and pins its HTTPS origin. The Hub installer should use that API when enabled. The existing RFC 7591 registration flow remains additive and unchanged; it still requires `clients:add` and creates a new client on each successful request, so it remains an operator-managed fallback rather than an idempotent Hub provisioning API.

Do not add a Hub-specific exception to `/connect/register`, infer Hub ownership from `client_name`, `app_id`, callback URL, requested scopes, or a caller-supplied profile string, or write OAuth clients directly to the database. Do not broaden `clients:add` into an application permission. The existing endpoint and standalone registration modes remain unchanged.

## Evidence in the current implementation

- `POST /connect/register` authorizes admin mode with a user permission (`clients:add`), an ungated admin client, or a service identity carrying that same permission (`src/http/routes.ts`). It has no NexusHub-specific authorization branch.
- The endpoint generates a random client ID and secret for each accepted request. There is no idempotency key, named-profile lookup, or repeatable secret recovery operation.
- `OAuthClient` records an optional `appId`, but no owner service identity, issuer-enrolled Hub identity, tenant/organization ownership, provisioning profile, or idempotency key (`src/domain/models.ts`). The optional app association is not proof that the caller owns that app.
- The existing adoption script uses the standard endpoint and documents the broad permission and operator recovery procedure (`scripts/nexushub-register-client.mjs`, `docs/NEXUSHUB_ADOPTION.md`).

These gaps make an API that accepts a Hub name or declared `profileId` unsafe: any caller with access to the proposed route could claim the Hub namespace, and retry after an ambiguous response could create duplicate clients or lose the one-time secret.

## Required upstream primitives

Before NexusHub can provision clients without a human administrator, NexusID must provide all of the following:

1. **A dedicated machine authority.** Define a permission such as `nexushub:clients:provision` and a non-user service identity credential that can receive only this permission. The authority must be granted by a NexusID administrator through the supported admin interface. It must not imply `clients:add`, role/user management, app assignment, signing-key control, or arbitrary OAuth-client mutation.
2. **Issuer-established ownership.** NexusID must bind the provisioning principal to an approved Hub installation (or to an explicit NexusID tenant and Hub installation). The API must derive that binding from authenticated server-side state. A caller-provided client name, profile ID, app ID, redirect URI, organization ID, or tenant ID alone is not ownership evidence. If NexusID cannot attest a Hub installation, provisioning remains operator-only.
3. **A transactional named-profile lifecycle.** Accept a versioned profile under the bound installation and atomically create-or-return the same client for the same installation/profile/version. Reusing the key with a different normalized registration body must return a conflict, not mutate an existing client. A retry must not create a second client.
4. **Safe credential recovery.** Define how a retry handles the client secret after a lost response. Either return a secret only once and provide an explicit authenticated rotate-and-return operation, or retain it using a documented secret-at-rest design that permits recovery. Never return a stored secret merely because a caller knows a client ID/profile name. Rotation must invalidate the prior secret atomically and be auditable.
5. **Lifecycle and audit controls.** Specify revocation/deprovisioning, profile-version upgrades, collision behavior, audit actor/target fields, and rate limits. Emit audit events for create, idempotent replay, conflict, rotation, and revoke without logging credentials.

## Implementation sequence and proposed storage/API boundary

This is the concrete NexusID-side change set required to implement the primitives above. It is a design contract, not an authorization to add the endpoint before the enrollment and transaction rules are in place.

1. **Add an explicit Hub enrollment record.** Introduce a durable `nexushub_installations` record with a generated installation ID, active/revoked state, the bound service-identity ID, the enrolled Hub issuer/origin, allowed profile IDs and versions, and creation/revocation timestamps. The service-identity binding must be unique and immutable after enrollment; transferring ownership requires an explicit NexusID-admin revoke-and-enroll operation. Enrollment is performed in NexusID Admin (or an equivalent separately authenticated administrative flow), never by the prospective Hub provisioning credential. The Hub-origin value is an audit/configuration attribute, not authentication by itself.
2. **Add a separate provision permission and verifier.** Do not encode `nexushub:clients:provision` as an ordinary role permission and pass it through `hasAdminPermission`: that helper recognizes `*:*`, `resource:*`, and exact `resource:action`, while app-bound role permissions are rewritten by `canonicalizeRolePermission`. Implement a dedicated service-identity authorization check that requires an active credential, the dedicated authority grant, and an active installation enrollment bound to that exact service identity. Existing `clients:add` remains insufficient; admin users manage enrollment but do not gain a machine provisioning path implicitly.
3. **Add a named profile binding with a database uniqueness guarantee.** Store a `nexushub_client_profiles` record keyed by `(installation_id, profile_id, profile_version)`, with a unique OAuth client ID, a canonical request digest, the validated profile version, state, and timestamps. Add a uniqueness constraint in each supported database schema/migration; application-level check-then-create alone is not concurrency-safe. Extend `OAuthClient` only with a nullable Hub-profile relation/marker needed for referential integrity and administration. Do not repurpose `app_id`: it is optional app association, not ownership evidence. Existing OAuth clients must remain readable and usable with no Hub profile row.
4. **Expose a versioned admin API only after the above exists.** Example boundary: `PUT /api/admin/v1/nexushub/client-profiles/{profileId}` with a versioned, bounded body. The server gets installation ownership solely from the authenticated service identity's enrollment, not from request fields. Validate the normalized body against an issuer-reviewed profile allowlist (client grants, scopes, callback origin, PKCE, auth method, TTL); reject unknown fields. In one database transaction, insert the profile binding and OAuth client, or load the existing binding: same key plus same canonical digest returns the stable client metadata without a second client; same key plus a different digest returns `409 Conflict` with no mutation. Never mutate an existing client's redirect URIs, grants, scopes, or secret during an idempotent replay.
5. **Make secret issuance recoverable without revealing a stored secret.** Current OAuth client secrets are stored as plaintext in `oauth_clients.secret` and compared by the authentication paths (`src/domain/models.ts`, `src/repositories/sqlite.ts`, `src/services/auth-service.ts`, and `src/http/routes.ts`). Therefore merely adding a secret hash to the profile table would not protect the current OAuth secret at rest. The first version should return the generated secret once, persist only the client-side secret as existing OAuth requires, and provide a separate installation-bound `rotate-and-return` operation if the initial response was lost. Rotation must atomically replace the secret, return it only in that response, invalidate the previous value immediately, and write an audit event. A later secret-at-rest redesign can change this tradeoff across all OAuth clients, but must not be smuggled into Hub provisioning alone.
6. **Audit from the transaction boundary.** Add events for enrollment, revoke, create, identical replay, digest conflict, rotate, and deprovision, recording the NexusID actor, installation ID, profile key/version, client ID, outcome, and request correlation ID. Do not record access tokens, client secrets, authorization headers, or secret digests that could become credential verifiers. Apply rate limits per installation and expose a NexusID-admin review/revoke path.

### Existing implementation facts that affect the design

- Service identities are represented as service-user records with metadata stored in user custom attributes; `ServiceIdentityService` grants credentials but has no NexusHub enrollment semantics. Do not make arbitrary metadata or `ownerId` an ownership assertion.
- The service-identity token path resolves role permissions for the service user. That path is for ordinary API authorization and does not establish that a service identity owns a Hub installation.
- OAuth clients are stored in the `oauth_clients` table. Current schema has `app_id`, but no owner, installer, profile key, unique profile tuple, or idempotency digest. The client repository contract offers create/find/update/list, but no transaction-scoped create-or-return operation.
- `POST /connect/register` creates a random client ID and secret and calls `ClientService.createClient`; this operation is not idempotent. Any proposed Hub endpoint must be additive and must not change this RFC 7591 behavior or the default-disabled registration mode.
- NexusID presently stores OAuth client secrets in clear text for authentication. One-time response handling is possible, but at-rest confidentiality requires a separate cross-client storage/authentication migration.

### Source-backed implementation feasibility (2026-10-22)

The following code paths were checked before deciding whether the endpoint could be added safely now:

- `AuthService.issueServiceIdentityClientCredentialsTokens` in `src/services/auth-service.ts` verifies an active service-identity credential and emits a client-credentials JWT. Its authority is the identity's ordinary `allowedScopes` and role permissions; the route that handles `/connect/register` then resolves `clients:add`. There is no dedicated capability/grant verifier for this operation. A new route must not call `hasAdminPermission` with `clients:add`, or use a role wildcard, as a substitute for Hub enrollment.
- `src/security/jwt.ts`'s service-identity token includes both the service-identity subject and client credential identity. That is sufficient to identify an authenticated credential after token verification, but it does not assert which Hub installation it represents. It only includes an audience when the service identity has configured allowed audiences, so a dedicated Hub audience must be explicitly enrolled and required by the new verifier. The proposed enrollment must bind the exact NexusID service identity and credential client ID; it must not trust a Hub ID, origin, or owner value supplied on each provisioning request.
- `ClientService.createClient` in `src/services/client-service.ts` validates redirect URIs and delegates to `ClientRepository.create`; the repository contract in `src/repositories/contracts.ts` exposes no transaction-scoped create-or-return or profile lookup. The `PrismaClientRepository` in `src/repositories/prisma-repositories.ts` creates the client separately. A second profile insert after this call could fail while leaving an orphan OAuth client, so application-level check-then-create is not an acceptable idempotency guarantee.
- `oauth_clients` is represented as an ignored/legacy model in `prisma/schema.prisma` and includes existing relationships to tokens and sessions. Custom schema setup differs across SQLite's `SqliteDatabase.migrate` and the PostgreSQL/MySQL runtime schema paths. A new ownership/profile relation therefore needs provider-specific schema rollout and transaction behavior verified against all supported providers; it cannot safely be hidden inside an endpoint-only patch.
- `AuditEvent.actorType` in `src/domain/models.ts` currently allows only `user | client | system`, while service-identity auth is separately represented in JWT claims. Existing audit logging can record a credential client ID, but dedicated enrollment/provision/rotation/revoke semantics need explicit event types and an unambiguous actor/installation/profile tuple. Secrets, token values, and secret digests must be excluded.
- OAuth client `secret` is the active clear-text verifier used by authentication. The service-identity credential repository instead stores a one-way hash, but that pattern cannot be copied for OAuth clients without changing client-authentication storage. Product/security owners must choose between explicitly accepting the existing OAuth secret-at-rest model for Hub clients or completing a cross-client verifier/secret-management redesign. Until that choice is made, do not claim the Hub path has at-rest secret protection.

#### Concrete first implementation boundary

Once the open choices above are decided, implement the following as one gated feature rather than incrementally exposing an unsafe endpoint:

1. A NexusID administrator enrolls a dedicated service identity and one credential. NexusID generates the immutable installation UUID, pins the Hub HTTPS origin, and selects a finite allowed profile/version set. The enrollment operation must reject bootstrap-admin identities and service identities already enrolled elsewhere. The Hub stores the returned installation UUID plus the issuer-issued client credential; caller-provided installation IDs are never authoritative.
2. Add a dedicated machine authorization check requiring a verified NexusID service-identity JWT whose subject and credential client ID exactly match the active enrollment, plus a dedicated `nexushub:clients:provision` grant on that enrollment. Neither `clients:add`, admin wildcards, a generic role permission, `app_id`, nor a Hub-supplied profile name alone grants access. Do not include the new grant in ordinary service identity role resolution.
3. Define a closed, versioned NexusHub relying-party profile allowlist in NexusID. The initial Hub profile fixes the callback suffix, exact grants (`authorization_code`, `refresh_token`, and opt-in `token_exchange`), PKCE, `client_secret_post`, and allowed scope names. The enrollment's pinned origin supplies the callback origin; request bodies cannot widen it. Reject unknown fields and cap request body size before parsing.
4. Persist profile ownership keyed by `(installation_id, profile_id, profile_version)` with a database unique constraint and canonical configuration digest. In the same transaction, insert the OAuth client and profile row. Identical retries return stable public client metadata; a changed digest returns conflict without mutation. Preserve existing `/connect/register` and general client management behavior.
5. Design the secret response lifecycle before implementation. Create and rotation operations use caller-provided idempotency keys scoped to enrollment/profile. If a response is lost, the exact same authorized key must recover the same generated value without creating a second client or rotating again; a new key intentionally rotates and invalidates the prior secret. Persist only what the selected secret-at-rest design requires, and audit create/replay/conflict/rotation/revoke without logging the secret or a verifier digest.
6. Add explicit, bounded NexusID audit events with actor service-identity ID, credential client ID, generated installation ID, profile/version, outcome, and correlation ID. Add admin-only enrollment review, suspend/revoke, credential replacement, and profile disable paths. Revocation must be checked on every provisioning request, not only when the token was issued.

The unresolved security decisions are specifically: (a) the administrative enrollment UX and whether one service identity may ever represent more than one Hub instance (the safe initial default is one-to-one); (b) whether the Hub profile is fixed to the current nine-scope contract or operator-extensible under an issuer-owned allowlist; and (c) whether accepting NexusID's existing clear-text OAuth client-secret storage is acceptable for this privileged integration. Until those are answered and provider-specific atomic storage is implemented, the existing operator-authorized RFC 7591 adoption path is the only supported path.

The API should live under a versioned NexusID administration namespace, be disabled unless the scoped authority and Hub installation binding are explicitly configured, validate the issuer/audience and authenticated service identity, and accept only a bounded schema. Its allowlist must constrain grants to `authorization_code`, `refresh_token`, and the opt-in `token_exchange` profile, require PKCE, use `client_secret_post`, and constrain scopes and redirect origins to a reviewed Hub profile. Existing OAuth validation rules remain authoritative.

### Additive first provisioning API

The current source now includes an opt-in `PUT /api/nexushub/v1/client-profile` endpoint, enabled only with `NEXUSID_NEXUSHUB_PROVISIONING_ENABLED=true`. It validates the same active service-identity credential and installation binding as enrollment inspection, derives registration values from the pinned `nexushub:1` profile and enrolled HTTPS origin, and reserves an installation-derived OAuth client ID. The Hub supplies a client secret generated on its side. NexusID does not return the secret; retries with the same installation, reserved ID, profile, and secret return the same public profile metadata. A conflicting registration returns `409` without updating the existing client. `mode: adopt-existing` is limited to that same reserved ID and exact profile/secret match. The standard `/connect/register` behavior is unchanged.

The same isolated endpoint now also supports `liberide:1` when an issuer administrator includes a separate canonical HTTPS `liberideOrigin` in the NexusHub service-identity enrollment. It pins exactly `${liberideOrigin}/api/auth/nexusid/callback`, scopes `openid profile email`, `authorization_code`, PKCE, and `client_secret_post`. It has a profile-specific deterministic client ID and shares the same secret-safe ensure/adopt semantics. The callback and scope contract is grounded in the reviewed Chatllm LiberIDE server handoff and its `configureNexusHubIdentity` source; there is no refresh-token usage there, so no refresh grant is approved. The new origin is mandatory for this profile and is never accepted on the machine profile request itself.

The profile write is one OAuth client-row insert; the reserved primary key is its idempotency boundary, so concurrent retries cannot create duplicate clients. This avoids a separate profile table or cross-table transaction for the fixed one-profile-per-installation v1 contract. Secret values continue to use NexusID's existing OAuth client storage behavior, including its existing at-rest limitations. This slice deliberately provides no rotation endpoint: operator-managed rotation must be coordinated, and a managed rotation API still needs a durable recoverable response lifecycle. Audit records record installation/profile/client identifiers and outcomes only; they do not include a secret or a secret-derived verifier.

## Acceptance criteria to unblock

- A service identity with only the dedicated permission can provision a bound Hub profile; one with `clients:add` alone cannot call the new endpoint unless explicitly granted the new authority.
- The server derives installation ownership from its enrollment record and rejects caller-selected identities outside that binding.
- Concurrent identical requests create exactly one client; an identical retry returns the defined stable result; a changed body under the same profile key conflicts without mutation.
- A lost first response has a documented, authenticated, auditable recovery path that does not expose the secret to another Hub installation.
- Existing `/connect/register` behavior and deployments with dynamic registration disabled remain unchanged.
- Schema uniqueness prevents concurrent duplicate `(installation, profile, version)` creation on SQLite, PostgreSQL, and MySQL; the repository API exposes a transaction-scoped operation and migration rollback/recovery behavior is documented.
- Enrollment can only be created/revoked by NexusID administrative authority, is bound to one active service identity, and cannot be claimed by a caller-selected installation/profile field.
- The secret-at-rest limitation is explicitly accepted for the initial release or resolved through a cross-client secret storage/authentication migration; it is not described as secret-hash protection while the active OAuth client secret remains plaintext.

Until these criteria are implemented and reviewed, the Hub installer must require an operator-provided NexusID admin credential for the existing additive adoption flow and must retain its ambiguous-outcome reconciliation behavior.

### Repository/API implementation contract (2026-10-23)

The follow-up repository inspection confirmed that the new `src/services/nexushub-client-profile.ts` closes profile derivation, but does not provide persistence or secret handling. The active `ClientRepository` in `src/repositories/contracts.ts` has only standalone `create`, `findById`, `update`, and `delete` calls. `ClientService.createClient` delegates to it without a transaction context. Therefore a profile row cannot currently be committed atomically with its `oauth_clients` row. The existing enrollment route still stores the binding in service-identity metadata and only exposes enrollment inspection; it is not a profile lifecycle API.

Do not implement a check-then-create shim on top of those methods. The minimal durable boundary should be a dedicated repository operation, implemented separately for SQLite and Prisma-backed PostgreSQL/MySQL, with the transaction object passed through every write:

```ts
interface NexusHubClientProfileRepository {
  ensure(input: {
    installationId: string; profileId: "nexushub"; profileVersion: 1;
    configurationDigest: string; client: OAuthClient;
  }): Promise<{ outcome: "created" | "replayed" | "conflict"; client?: OAuthClient }>;
  rotate(input: {
    installationId: string; profileId: "nexushub"; profileVersion: 1;
    idempotencyKey: string; requestDigest: string; newSecret: string;
  }): Promise<{ outcome: "rotated" | "replayed" | "conflict"; clientId?: string; secret?: string }>;
}
```

The schema needs an issuer-owned installation table and a profile table with a primary/unique key on `(installation_id, profile_id, profile_version)`, a unique `client_id`, immutable configuration digest, and lifecycle state. The profile references the OAuth client. The idempotency record for each rotation needs a unique `(installation_id, profile_id, profile_version, idempotency_key)` key, request digest, and a result reference. Installation ownership and profile version are looked up from those tables after authenticating the enrolled service identity; they are never accepted as authority from the request body. A digest mismatch at either unique key returns conflict and makes no changes.

`ensure` must perform profile-row reservation, OAuth client insert, and profile finalization in one database transaction. On a unique-key race it must roll back the losing client insert, reload the winning profile, and compare the canonical digest before returning replay or conflict. SQLite must use one connection and a write transaction (`BEGIN IMMEDIATE` or equivalent); Prisma providers must use `$transaction` and transaction-scoped raw queries/delegates. MySQL must use InnoDB uniqueness and lock semantics. Do not catch a uniqueness error and continue in the same failed transaction, especially on PostgreSQL. Existing `ClientRepository` and `/connect/register` callers retain their behavior; the new operation must not be built by changing the semantics of generic client creation.

The current secret lifecycle cannot satisfy lost-response recovery safely as a one-time secret: NexusID has no encryption-at-rest secret manager or encrypted result store, and OAuth client authentication still reads `oauth_clients.secret` as clear text. A one-way hash does not enable replay of the exact response. Returning the existing clear-text database value on an idempotency retry would turn database-readable credential material into an implicit recovery API and requires an explicit security decision that has not been made. Thus no ensure/rotate persistence or HTTP route is added in this slice.

Before enabling that API, choose and implement one of these complete secret policies:

- **Encrypted replay result:** inject a KMS/envelope-encryption interface with key versioning and authenticated encryption. Persist the OAuth verifier using the same supported secret-at-rest migration, and store the exact response secret encrypted against the rotation idempotency record. Bind associated data to installation, profile, version, key, and request digest. Only the matching active enrollment may replay it; expire the encrypted response after a bounded recovery window and erase its ciphertext on expiry. Rotation plus OAuth verifier replacement plus replay-result creation must commit atomically. KMS unavailability must fail closed before any mutation.
- **One-time return with explicit re-rotation:** persist only the active OAuth verifier as required by the current auth implementation, never return it on replay, and require an independently authenticated rotate operation to issue a replacement. This is acceptable only if the issuer explicitly accepts the existing plaintext-at-rest model, and if the rotate request itself has a durable state machine that cannot rotate twice after an ambiguous response. Without encrypted replay, the server cannot both rotate once and recover the same response after a lost response; the API must make this operational tradeoff explicit instead of claiming retry safety.

The required concurrency suite must use two independent repository instances/connections against the same database and exercise: simultaneous identical ensure (exactly one OAuth client and one profile); simultaneous same-key/different-digest ensure (one winner, one conflict); injected failure between client insert and profile finalization (no orphan client); simultaneous same-idempotency-key rotation (one rotation and the same recoverable result only under the selected encrypted policy); changed request under a reused rotation key (conflict, no secret change); a second key rotation (old secret immediately invalid, new secret valid); and revoked enrollment racing with provisioning (no successful mutation after the revoke takes effect). Run it against SQLite and every configured Prisma provider before marking the storage boundary complete. Provider-skipped tests are not evidence for provider support.

The fixed-profile API is supported for ensure and exact adopt-existing operations. Do not expose managed secret rotation until an explicit recoverable rotation lifecycle is implemented and verified across supported database providers.

### Current source-level gate

The issuer now has an opt-in enrollment foundation, disabled unless `NEXUSID_NEXUSHUB_PROVISIONING_ENABLED=true`. NexusID admins bind one active service-identity credential to a canonical HTTPS Hub origin; the server generates the installation UUID and pins the `nexushub:1` profile. A Hub bearer-token endpoint rechecks the service-identity subject, credential client ID, active enrollment, and dedicated audience on every lookup. Enrollment and revocation are audited. The routes use existing `service_identities:change` and `service_identities:delete` administrator permissions and do not use `clients:add`.

Enrollment remains stored in protected service-identity metadata rather than a normalized cross-identity installation table. The single fixed profile is bound to an installation-derived reserved client ID, with the OAuth client primary-key constraint providing the create/replay serialization point. This v1 endpoint accepts a Hub-generated secret and never returns stored secret material; it does not support managed rotation or encrypted response recovery. Profile create and replay audit events contain no secret or secret-derived verifier. The Hub must continue to retain its own secret privately and coordinate any secret change through the existing issuer administrator controls. The mutating `scripts/nexushub-register-client.mjs` fallback still requires `NEXUSID_ACKNOWLEDGE_BROAD_CLIENTS_ADD=true`; read-only preflight does not.
