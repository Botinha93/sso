# NexusBus management tokens from NexusID

## Status

An opt-in issuer endpoint now supports a dedicated `nexusbus_management` grant. It is disabled unless `NEXUSID_NEXUSBUS_MANAGEMENT_ENABLED=true`. NexusID only accepts an enrollment mapping that exactly matches a deployment-admin configured entry in `NEXUSID_NEXUSBUS_MANAGEMENT_BINDINGS_JSON`; it rechecks that entry before every token mint. Ordinary OAuth client credentials and delegated-user exchange are not accepted by this grant.

## Authority and routes

The approved JSON mapping is a deployment-owned registry. Each entry pins `organizationId`, optional `projectId`, Bus `tenant`, Bus `app`, and the maximum allowed roles (`nexusbus.installation.read` and/or `nexusbus.installation.apply`). The NexusID platform administrator who controls deployment configuration approves the mapping. The NexusID service-identity administrator then creates an enrollment at `PUT /api/admin/service-identities/{id}/nexusbus-management-enrollment`; submitted fields must match the registry exactly and roles may only be a subset. The response contains a generated 256-bit secret once. NexusID stores only its SHA-256 verifier in `nexusbus_management_enrollments`.

The Hub requests a token from `POST /api/nexusbus/v1/token` using `grant_type=nexusbus_management`, the one-time returned credential ID as `client_id`, the generated secret as `client_secret`, and a non-empty subset of enrolled roles. The issuer derives all authority claims from enrollment and the current registry: exactly `aud=nexusbus-management`, a non-empty installation subject, `tenant`, `app`, `roles`, and `hub_scope` with the bound organization and optional project. The token has a fresh `jti` and a five-minute maximum lifetime. Role escalation, unknown grant types, inactive identities, invalid secrets, revoked enrollment, and a removed registry binding fail closed. Enrollment creation, revocation, token success, and denial are audited without recording the secret or bearer token.

Revoke an enrollment with `DELETE /api/admin/service-identities/{id}/nexusbus-management-enrollment`. This prevents future token minting. Already issued tokens can remain valid for up to five minutes unless NexusBus also checks `jti` revocation.

## Persistence limitation

The dedicated `nexusbus_management_enrollments` table is initialized by provider-neutral startup DDL when the Prisma-backed repository bundle starts. It has unique constraints for enrollment, installation, service identity, and management credential IDs. The repository inserts enrollment rows atomically and uses conditional updates for revocation. SQLite, MySQL 8.0, and PostgreSQL 17 startup/create/read/revoke behavior passed focused acceptance; full SQLite unit/integration and MySQL unit/integration/E2E suites passed. Enrollment creation remains one-time per service identity, including after revocation; a same-enrollment replacement credential now uses the separate audited stage/activate lifecycle below, while revoked enrollments remain terminal.

The environment registry is also a deployment trust input: NexusID cannot independently verify that a Bus tenant or app exists. The operator must source these identifiers from the trusted NexusBus identity administration process. This implementation does not infer them from Hub requests, manifests, generic OAuth metadata, or service-identity role assignments.

## Credential overlap rotation (2026-10-23)

The dedicated enrollment now supports an additive replacement credential lifecycle without changing ordinary OAuth client credentials or the standalone service-identity APIs. `POST /api/nexusbus/v1/management-credential-rotations` requires the active management credential and an exact same-enrollment replacement ID plus secret; NexusID stores only the verifier and accepts both old and pending credentials during overlap. `POST /api/nexusbus/v1/management-credential-rotations/activate` requires the pending credential, is retry-safe after commit, switches the active ID/hash, and stops accepting the former ID. Both operations recheck service identity status and the configured Bus binding and audit credential IDs only. Enrollment revocation rejects both IDs.

Hub writes the candidate secret to its protected credential map before issuer stage, supports a map-backed worker resolver, and persists an owner-authorized active credential reference separately from the immutable enrollment-proof credential reference. Hub reconciliation reads that active reference. The live cross-repository acceptance in `nexusBust/apps/nexusbus/test/hub-enrollment-live.test.ts` proves old/new overlap, persistence after NexusID Prisma disconnect/reconnect between stage and activation, duplicate activation retry, old-ID denial after activation, the Hub owner-session/CSRF-protected pointer update, Bus policy revocation with the new credential, issuer revocation denying both IDs before old-secret retirement, and child-process private-file resolution with only a hash emitted and no secret in argv. Command: `NEXUSBUS_HUB_ENROLLMENT_ACCEPTANCE=1 NEXUSBUS_TEST_DATABASE_URL='postgres://postgres:<password>@127.0.0.1:5432/postgres' bun test apps/nexusbus/test/hub-enrollment-live.test.ts` (1 test, 48 assertions, disposable PostgreSQL).

This does not establish production browser login or a deployed issuer/Hub rotation. The acceptance uses a local OIDC issuer fixture. Hub's live reconciliation requests a token and exercises NexusBus authorization as its probe; there is not yet a separate pre-activation Bus permission probe. Process recovery is tested by repository reconnect and idempotent HTTP replay, not forced termination at every side-effect boundary. Hub's local private-file map still requires operator backup and recovery. NexusID Hub OAuth client-secret rotation is a distinct lifecycle and is not covered by this management-credential rotation.

## Hub challenge assertion primitive (owner consent is not asserted)

When `NEXUSID_NEXUSBUS_MANAGEMENT_ENABLED=true`, `POST /api/nexusbus/v1/management-enrollment-proof` accepts the dedicated credential, an opaque 32–128 character base64url challenge, and `hub_instance_id` returned with that owner-authorized Hub challenge. NexusID rejects additional request fields, verifies the dedicated credential against the active enrollment, checks the current deployment registry and active service identity, and requires the same identity to have an active NexusHub installation enrollment. NexusID derives its issuer-assigned Hub installation ID and the complete Bus binding from issuer records; the caller cannot select a project, tenant, app, role, or issuer-owned installation ID.

The RS256 assertion uses protected `typ=nexusbus-management-enrollment-proof.v1+jwt`, issuer equal to the configured NexusID issuer, audience `nexushub-nexusbus-management-proof`, service identity subject, random `jti`, the exact challenge, the issuer-assigned NexusID Hub installation ID, the challenge's immutable Hub instance ID, and an `enrollment` object containing enrollment ID, immutable Bus binding, revision, and status. The IDs are distinct by design. Lifetime is 60 seconds. Revision is 1 while the one-time enrollment is active; revoked enrollments cannot obtain a new proof. The existing model permits only one irreversible revoke and no re-enrollment, so it does not claim a general revisioned lifecycle.

This is issuer evidence only. It explicitly includes `owner_consent: "not_asserted"`; NexusID cannot observe or validate Hub owner consent from the current protocol. The Hub instance ID accompanies a random one-use challenge generated and stored by Hub; NexusID signs both this value and its own issuer-assigned Hub installation ID. Reissuing an assertion for the same challenge is possible; replay prevention is the Hub's responsibility and requires signature verification plus an atomic consume of the exact stored challenge bound to the Hub instance, organization, and project. The Hub must also independently establish current consent and current status/revocation semantics before apply. No NexusBus apply path may be enabled by this issuer primitive alone. Hub still needs safe durable secret references and an online/current issuer status or revocation check; signed status at mint time alone is a bounded-staleness snapshot.
